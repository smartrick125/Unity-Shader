## 流程卡记录

### 流程：URP 后处理架构与执行时序

**一句话流程：**

`RendererFeature` 创建并注入 `RenderPass`，`RenderPass` 在 Render Graph 中声明资源与执行步骤，最后由 Shader 在 GPU 上完成处理并把结果写回相机颜色目标。

**适用环境：**

- Unity 版本：Unity 6000.0+（Unity 6）
- 渲染管线及版本：URP 17+，Render Graph 启用
- 渲染路径：当前记录不依赖特定 Forward/Deferred 路径
- 脚本性质：Runtime 后处理管线控制与渲染脚本

**完整流程：**

```text
[初始化阶段：通常在 RendererFeature 创建或重建时执行]
GaussianBlurRendererFeature.Create()
↓
创建 Material
↓
实例化 GaussianBlurRenderPass
↓
设置 renderPassEvent = AfterRenderingSkybox

[每相机每帧的录制与执行阶段]
Volume 框架更新 GaussianBlur_CustomValumeComponent 参数
↓
GaussianBlurRendererFeature.AddRenderPasses()
↓
过滤 CameraType.Game 后 EnqueuePass()：只加入当前相机的 RenderPass 队列，不立即绘制
↓
URP 按 renderPassEvent 对入队的 ScriptableRenderPass 进行稳定排序
↓
GaussianBlurRenderPass.RecordRenderGraph()
↓
获取 activeColorTexture 与相机目标描述符
↓
创建临时纹理并更新 Material 参数
↓
录制纵向模糊：相机颜色 → 临时纹理，Shader Pass 0（尚未由 GPU 绘制）
↓
录制横向模糊：临时纹理 → 相机颜色，Shader Pass 1（尚未由 GPU 绘制）
↓
Render Graph 收集完整任务图，分析资源依赖与临时资源生命周期
↓
执行到对应任务：封装版由 AddBlitPass 内部回调提交命令；手动版回调 ExecutePass()
↓
ExecutePass() 向 CommandBuffer 记录 Blit / Draw 命令，回调是“稍后由 Render Graph 调用已声明的方法”，不是重新声明
↓
GaussianBlur.shader 在 GPU 上完成采样并写回相机颜色目标
```

**组件职责：**

| 组件 | 类型 / 层级 | 核心职责 |
| :--- | :--- | :--- |
| `GaussianBlurRendererFeature` | `ScriptableRendererFeature` / C# 调度层 | 创建与销毁材质、实例化 RenderPass、设置注入位置并过滤相机类型。 |
| `GaussianBlur_CustomValumeComponent` | `VolumeComponent` / 参数层 | 保存和插值 `iterations`、`blurSpread`、`downSample` 等动态参数。 |
| `GaussianBlurRenderPass` | `ScriptableRenderPass` / Render Graph 封装版 | 使用 `RenderGraphUtils.AddBlitPass` 录制纵向和横向 Blit；当前 RendererFeature 实际使用该版本。 |
| `GaussianBlur_RenderPass1` | `ScriptableRenderPass` / Render Graph 手动版 | 使用 `AddRasterRenderPass` 显式声明纹理读写、颜色附件和执行回调。 |
| `RenderGraph` | C# / 任务与资源调度层 | 先收集 Pass 及其读写依赖，再统一安排执行顺序、临时资源生命周期与执行回调。 |
| `ExecutePass` | C# / Render Graph 执行回调 | 在 Render Graph 执行到手动 Raster Pass 时被调用，向 CommandBuffer 记录命令；它不是 GPU Shader 本身。 |
| `GaussianBlur.shader` | ShaderLab / HLSL / GPU 执行层 | Pass 0 执行纵向模糊，Pass 1 执行横向模糊。 |

**关键输入与输出：**

| 阶段 | 输入 | 输出 / 影响 |
| :--- | :--- | :--- |
| Volume 参数更新 | Volume Override 或 `GaussianBlurSettings` 默认值 | Material 中的 `_Iterations`、`_BlurSpread`、`_DownSample`。 |
| Render Graph 资源准备 | `activeColorTexture`、相机目标描述符 | 无深度缓冲的临时高斯模糊纹理。 |
| 纵向模糊 | 相机颜色纹理、Material、Shader Pass 0 | 写入临时纹理。 |
| 横向模糊 | 临时纹理、Material、Shader Pass 1 | 写回相机颜色目标。 |

**执行阶段与顺序：**

- 注入位置：`RenderPassEvent.AfterRenderingSkybox`。
- 前置依赖：有效的 Game Camera、Material、`activeColorTexture`，且当前目标不是 Back Buffer。
- 执行顺序：纵向模糊必须先写入临时纹理，横向模糊再读取临时纹理并写回相机颜色。
- 调度边界：`EnqueuePass()` 只将 `ScriptableRenderPass` 加入当前相机队列；`RecordRenderGraph()` 只登记任务和资源依赖；轮到该任务时才回调执行函数并提交 GPU 命令。
- 执行频率：`Create()` 通常只在初始化或重建时执行；`AddRenderPasses()` 与 `RecordRenderGraph()` 按相机、按帧调用。

**实现方式对比：**

| 对比项 | `GaussianBlurRenderPass` | `GaussianBlur_RenderPass1` |
| :--- | :--- | :--- |
| 所在文件 | `GaussianBlur_RenderPass.cs` | `GaussianBlur_RenderPas1.cs` |
| 录制入口 | `RenderGraphUtils.AddBlitPass` | `RenderGraph.AddRasterRenderPass` |
| 资源声明 | 由 `AddBlitPass` 封装 | 手动调用 `UseTexture`、`SetRenderAttachment` |
| 执行方式 | 工具方法内部完成 Blit 执行 | `SetRenderFunc` → 静态 `ExecutePass` → `Blitter.BlitTexture` |
| 传递数据 | `BlitMaterialParameters` | 自定义 `PassData` |
| 代码特点 | 简短，适合常规全屏材质 Blit | 步骤显式，适合学习底层流程或增加自定义资源与附件 |

两种写法使用同一个 Material，并依次运行 Shader Pass 0 和 Pass 1。区别在于 CPU 侧如何向 Render Graph 描述渲染步骤，不在高斯模糊算法本身。

**常见坑：**

- `EnqueuePass()` 每次把一个 `ScriptableRenderPass` 加入当前相机队列，并不立即绘制；这个 RenderPass 随后可以在一次 `RecordRenderGraph()` 中登记一个或多个 RenderGraph 任务节点，因此“一个入队 RenderPass”不等于“一个 RenderGraph 节点”。
- `SetRenderFunc` 保存的是稍后调用的回调；回调不是重新声明方法。`CameraType.Game` 也只限定游戏相机类型，不等于 `Application.isPlaying`。
- `TextureHandle.IsValid()` 只说明句柄已注册，不保证纹理内容正确；仍需检查资源来源、读写顺序和相机目标状态。

**验证方式与结果：**

- 源码静态检查：已确认两个实现都录制“相机颜色 → 临时纹理 → 相机颜色”的纵向、横向双 Pass 数据流。
- Frame Debugger：未在 Unity 中验证。封装版应显示 `VerticalGaussianBlurRenderPass`、`HorizontalGaussianBlurRenderPass`；手动版应显示带 `_Manual` 后缀的对应事件。
- Profiler：未在 Unity 中验证。实际 CPU 与 GC 表现应分别启用两种实现后测量，不能仅根据代码长度判断性能。

**是否需要深挖：**

当前重点：

- 掌握 `RendererFeature → RenderPass → Render Graph → Shader → 相机颜色目标` 的完整职责链。
- 掌握“创建对象 → 入队 → 录制 Render Graph 任务 → 回调记录 CommandBuffer 命令 → GPU 执行”的阶段边界，以及两个模糊 Pass 的资源读写顺序。

暂时不用深挖：

- Render Graph 内部编译、Pass 合并、资源别名和底层图形 API 命令生成细节。

### 流程：URP Render Graph 跨帧累计动态模糊

**一句话流程：**

当前相机颜色先与长期保存的历史颜色混合并写回历史纹理，再把更新后的历史纹理复制回相机颜色；历史由跨帧 `RTHandle` 保存，每帧导入为当前 Render Graph 可使用的 `TextureHandle`。

**适用环境：**

- Unity 版本：Unity `6000.3.9f1`
- 渲染管线及版本：URP `17.3.0`，Render Graph 启用
- 渲染路径：当前记录不依赖特定 Forward/Deferred 路径
- 脚本性质：Runtime 自定义后处理与跨帧历史资源

**完整流程：**

```text
[初始化]
MotionBlurRendererFeature.Create()
↓
创建 Material，并 new MotionBlurRenderPass(material, defaultSettings)
↓
构造函数把 Material 与默认设置保存到 RenderPass 实例字段

[当前相机、当前帧]
AddRenderPasses() 将 MotionBlurRenderPass 加入 Game Camera 队列
↓
RecordRenderGraph(renderGraph, frameData)
↓
frameData.Get<UniversalResourceData>() 取得当前帧相机资源
frameData.Get<UniversalCameraData>() 取得当前相机描述数据
↓
从 cameraTargetDescriptor 复制尺寸与格式，去除深度并关闭 MSAA
↓
ReAllocateHandleIfNeeded(ref rTHandle, descriptor, ...)
创建或在尺寸、格式变化时重建跨帧历史 RTHandle
↓
ImportTexture(rTHandle) 把外部历史资源登记为本帧 TextureHandle
↓
[首次分配或重建]
activeColorTexture → Initialize Pass → history
↓
[普通帧]
activeColorTexture + history → Accumulation Raster Pass → history
↓
history → Copy Back Pass → activeColorTexture
↓
后续 URP Pass 与最终相机输出读取更新后的 activeColorTexture
```

普通帧的核心关系是：`新历史 = 当前帧 × 当前帧权重 + 旧历史 × 历史权重`。当前实现由 Shader 输出 `_BlurAmount` 作为源 Alpha，并通过硬件混合 `Blend SrcAlpha OneMinusSrcAlpha` 把当前颜色与历史颜色合成。

**组件职责：**

| 组件 | 类型 / 层级 | 核心职责 |
| :--- | :--- | :--- |
| `MotionBlurRendererFeature` | `ScriptableRendererFeature` / C# 调度层 | 创建 Material 和 RenderPass，设置注入位置，并把 Pass 加入 Game Camera 队列。 |
| `MotionBlurRenderPass` 实例字段 | C# / 跨调用状态 | 长期保存 `Material`、默认设置和跨帧 `RTHandle`。 |
| `frameData` | URP / 当前相机当前帧共享上下文 | 提供 URP 已准备的 `UniversalResourceData`、`UniversalCameraData` 等帧上下文。 |
| `PassData` | Render Graph / 单个任务节点执行数据 | 把该节点执行时需要的源、目标、Material 和 Shader Pass 索引传给执行回调。 |
| `RenderTextureDescriptor` | C# / 资源描述 | 描述历史颜色纹理需要的尺寸、格式、维度和采样等属性。 |
| `RTHandle` | SRP / 跨帧实际资源引用 | 持有可跨帧保留内容的历史渲染纹理。 |
| `TextureHandle` | Render Graph / 本帧资源引用 | 表示当前 Render Graph 中对相机颜色或导入历史纹理的引用。 |
| `MotionBlur.shader` | ShaderLab / HLSL / GPU 执行层 | 采样 `_BlitTexture`，输出当前颜色和混合权重，配合 Blend 更新历史颜色。 |

**关键输入与输出：**

| 阶段 | 输入 | 输出 / 影响 |
| :--- | :--- | :--- |
| 尺寸与格式准备 | `cameraData.cameraTargetDescriptor` | 与相机目标匹配、无深度、单采样的历史纹理描述符。 |
| 历史资源准备 | `descriptor`、原有 `rTHandle` | 可复用或重新分配的跨帧 `RTHandle`；返回值说明本次是否发生分配。 |
| 本帧资源登记 | `rTHandle` | 当前 Render Graph 可引用的 `accumulationTexture`。 |
| 累计节点 | 当前相机颜色、旧历史、Material、Shader Pass 0 | 写出更新后的历史颜色。 |
| 写回节点 | 更新后的历史颜色 | 覆盖当前相机颜色，供帧内后续阶段和最终输出使用。 |

**执行阶段与顺序：**

- 注入位置：当前代码设置为 `RenderPassEvent.AfterRenderingSkybox`。
- 前置依赖：有效的 Game Camera、Material、非 Back Buffer 的活动颜色目标，以及有效的相机目标描述符。
- 首帧或重建顺序：先用当前相机颜色初始化历史，避免读取未定义的历史内容，再写回相机颜色。
- 普通帧顺序：累计节点必须先更新历史，写回节点随后读取更新后的历史并写回相机颜色。
- 生命周期边界：`rTHandle` 跨帧保留；`ImportTexture()` 返回的 `TextureHandle` 只属于当前 Render Graph 记录周期。

**实现方式对比：**

| 对比项 | `RenderTextureDescriptor` | `RTHandle` | `TextureHandle` / `ImportTexture` |
| :--- | :--- | :--- | :--- |
| 本质 | 资源规格说明 | 可长期持有的实际资源引用 | 当前 Render Graph 中的资源引用 |
| 是否保存像素 | 否 | 是 | 本身不另存一份像素 |
| 主要作用 | 描述尺寸、格式、深度、MSAA 等 | 跨帧保留历史颜色 | 向本帧任务图声明并使用该外部资源 |
| 是否负责分配 | 否 | 由分配 API 创建或重建 | `ImportTexture()` 不负责分配、缩放或清空 |

三者是协作关系：描述符先说明“需要怎样的纹理”，`ReAllocateHandleIfNeeded` 据此维护 `RTHandle`，`ImportTexture` 再让本帧 Render Graph 能引用该资源。

**常见坑：**

- `passData.src = source` 只把句柄传给执行回调；仍需使用 `UseTexture()`、`SetRenderAttachment()` 声明节点的读取与写入依赖。
- “本帧其他位置使用目标纹理”是指稍后的 Pass、Shader 或最终相机输出会读取它；仅写入却无人读取的目标不会影响最终画面，并可能在允许剔除时被 Render Graph 移除。
- `ImportTexture()` 不会创建、调整尺寸、初始化或复制纹理；历史内容的初始化必须由独立写入步骤完成。
- 当前 `RTHandle` 尚未在 RenderPass / RendererFeature 销毁时显式释放；这是当前代码需要继续处理的资源生命周期问题。

**验证方式与结果：**

- 源码静态检查：已确认当前代码存在 Feature 创建与入队、描述符复制、`RTHandle` 重分配、本帧导入、初始化节点、累计节点和写回节点。
- Shader 静态检查：已确认 Shader 采样 `_BlitTexture`，输出 `_BlurAmount` 作为 Alpha，并使用 `Blend SrcAlpha OneMinusSrcAlpha` 更新保留内容的颜色附件。

当前重点：

## 概念卡记录

### 概念：RenderGraph

**一句话记忆：**

`RenderGraph` 是本帧整体渲染任务与资源依赖的管理器；各个 RenderPass 只向其中登记自己的部分任务。

**所在层级：**

Core SRP 的 `UnityEngine.Rendering.RenderGraphModule`，由当前 URP Render Graph 路径使用的任务与资源调度层。

**核心职责：**

- 收集 URP 内置和自定义 Pass 登记的渲染任务、资源读取与写入关系。
- 根据资源的生产者与使用者组织任务依赖，并管理临时资源生命周期。
- 执行到具体任务时由 CPU 调用已注册的执行回调；回调向 `context.cmd` 记录命令，Unity 提交后才由 GPU 运行 Shader 并完成绘制。

**参与流程：**

```text
RendererFeature 通过 EnqueuePass() 将 ScriptableRenderPass 加入当前相机队列
↓
URP 调用 ScriptableRenderPass.RecordRenderGraph(renderGraph, frameData)
↓
CPU 通过 AddRasterRenderPass() / AddBlitPass() 登记任务、资源依赖和执行回调
↓
RenderGraph 收集完整任务图并分析资源依赖
↓
执行到未被剔除的任务时，CPU 调用 ExecutePass() 等回调
↓
回调通过 context.cmd 向 CommandBuffer 记录 Blit / Draw 等命令
↓
Unity 将命令提交给图形系统
↓
GPU 随后运行 Shader 并写入渲染目标
```

**常用入口 / 搭配：**

- `ScriptableRenderPass.RecordRenderGraph(RenderGraph, ContextContainer)`
- `AddRasterRenderPass`、`AddBlitPass`、`UseTexture`、`SetRenderAttachment`
- `SetRenderFunc`、`TextureHandle`、`ContextContainer`

**它不负责什么：**

`RenderGraph` 不是 Shader、GPU 或单纯的顺序排序器；它负责组织本帧任务、资源依赖与生命周期。`ExecutePass()` 是 CPU 执行的回调，它负责记录 GPU 命令，不亲自计算纹理中的每个像素。

**易错点：**

- `RecordRenderGraph()`、执行回调和 GPU 绘制都发生在程序运行期间；这里的“录制阶段”不是 C# 编译阶段。
- 执行 `RecordRenderGraph()` 时，`SetRenderFunc` 只保存稍后调用的回调；轮到该任务时 CPU 才执行 `ExecutePass()`，而记录命令仍不等于 GPU 已完成绘制。
- 若任务最终结果无人使用且允许被 Render Graph 剔除，对应执行回调可能不会被调用；不能仅凭 `RecordRenderGraph()` 被调用就认定 GPU 已执行该 Pass。

**现阶段掌握边界：**

- 当前需要掌握：`RenderGraph` 不只是排序，还管理任务依赖与资源；并能区分“CPU 录制任务 → CPU 调用回调记录命令 → Unity 提交 → GPU 执行”。
- 暂时不用深挖：Render Graph 内部编译、Pass 合并、资源别名与底层图形 API 屏障细节。

**验证依据：**

- 已核对项目中的 `GaussianBlur_RendererFeature.cs`、`GaussianBlur_RenderPass.cs`、`GaussianBlur_RenderPas1.cs` 及 Core SRP Package 内的 `RenderGraph.cs`、`RenderGraphUtilsBlit.cs`。
- 当前项目为 Unity `6000.3.9f1`、URP `17.3.0`；`GaussianBlur_RenderPas1.cs` 中由 `SetRenderFunc` 登记 `ExecutePass()`，并在回调内调用 `Blitter.BlitTexture(context.cmd, ...)`。
- 未在 Unity 中使用 Frame Debugger 或 Render Graph Viewer 进行运行时验证。

### 概念：Raster Pass 的创建与资源声明作用域

**一句话记忆：**

`AddRasterRenderPass()` 创建的是 Render Graph 中的光栅化任务节点，并返回用于配置该节点的 `builder`；先有这个节点，后续资源读写声明和执行回调才能明确属于哪个 Pass。

**所在层级：**

Core SRP 的 Render Graph 录制层，由 URP 的 `ScriptableRenderPass.RecordRenderGraph()` 使用；这里的 Raster Pass 是逻辑任务节点，不是 ShaderLab 中的 Shader Pass。

**核心职责：**

- 创建并命名一个光栅化任务节点，确定它使用 `RasterGraphContext` 执行。
- 通过返回的 `builder`，把 `UseTexture()`、`SetRenderAttachment()` 和 `SetRenderFunc()` 关联到当前任务节点。
- 通过 `out PassData` 提供录制阶段到执行回调之间的数据载体，真正的命令在稍后的执行阶段记录。

**参与流程：**

```text
从 ContextContainer 取得相机资源，并按需求创建临时资源
↓
AddRasterRenderPass() 创建 Raster Pass 任务节点并返回 builder、PassData
↓
填充 PassData，声明当前节点读取什么、写入什么、执行哪个回调
↓
Render Graph 收集并分析任务图
↓
执行到该节点时调用回调记录光栅化命令
↓
GPU 随后执行 Shader 并写入颜色附件
```

**常用入口 / 搭配：**

- `RenderGraph.AddRasterRenderPass<PassData>()`
- `IRasterRenderGraphBuilder.UseTexture()`、`SetRenderAttachment()`、`SetRenderFunc()`
- `UniversalResourceData`、`UniversalCameraData`、`TextureHandle`、`RasterGraphContext`

**它不负责什么：**

创建 Raster Pass 不会立即创建画面结果或启动 GPU 绘制，也不是取得相机资源的必要前提。相机资源可以在 `AddRasterRenderPass()` 之前取得；必须先创建 Pass 的是“把资源读写关系登记到这个 Pass”这一步。

**易错点：**

- `RecordRenderGraph()` 不只是准备普通数据，它还在建立任务节点、资源依赖和执行计划。
- `frameData.Get<UniversalResourceData>()` 可以写在创建 Raster Pass 之前；教程放在 `using` 内主要是把当前 Pass 的配置集中表达。
- `passData.src = source` 是把资源传给执行回调，`builder.UseTexture(source)` 是向 Render Graph 声明依赖；二者用途不同，不能互相替代。

**现阶段掌握边界：**

- 当前需要掌握：创建 Raster Pass 是建立可配置的逻辑任务节点；资源获取可以提前，但资源读写声明必须依附具体 Pass 的 `builder`。
- 暂时不用深挖：Render Graph 编译后如何生成资源屏障、合并原生 Render Pass，以及底层图形 API 如何提交命令。

**验证依据：**

- 已核对 Core SRP Package 中 `RenderGraph.cs` 的 `AddRasterRenderPass()`，以及 `IRenderGraphBuilder.cs` / `RenderGraphBuilders.cs` 中的 `UseTexture()`、`SetRenderAttachment()` 接口。

### 概念：`AddBlitPass` 封装式 Blit Pass

**一句话记忆：**

`AddBlitPass()` 是 Render Graph 中用于“源纹理 → Material / Shader Pass 处理 → 目标纹理”的封装式全屏 Pass，它在内部完成数据传递、资源声明和执行回调注册。

**所在层级：**

Core SRP 的 `UnityEngine.Rendering.RenderGraphModule.Util.RenderGraphUtils`，由 URP Render Graph 路径中的 `ScriptableRenderPass.RecordRenderGraph()` 调用。

**核心职责：**

- 通过 `BlitMaterialParameters` 接收源纹理、目标纹理、Material 和 Shader Pass 索引。
- 在内部创建 PassData，并向 Render Graph 声明源纹理读取与目标纹理写入关系。
- 在 Render Graph 执行到该任务时，通过内部回调记录全屏 Blit 命令。

**参与流程：**

```text
RecordRenderGraph() 取得源纹理并创建目标纹理
↓
创建 BlitMaterialParameters(source, destination, material, shaderPass)
↓
AddBlitPass() 在内部创建 PassData、声明读写关系并注册执行回调
↓
Render Graph 分析任务与资源依赖
↓
内部回调记录 Blit 命令
↓
GPU 运行指定 Shader Pass 并写入目标纹理
```

**常用入口 / 搭配：**

- `RenderGraphUtils.BlitMaterialParameters`
- `RenderGraphUtils.AddBlitPass()`
- `TextureHandle`、`Material`、Shader Pass 索引
- URP 的 SRP Blit Shader 或兼容 `_BlitTexture` 输入的全屏 Shader

**它不负责什么：**

`AddBlitPass()` 不是高斯模糊算法本身，也不会在调用当下立即启动 GPU；它只封装了常规全屏 Blit 的 Render Graph 录制步骤。需要自定义多附件、特殊资源声明或执行命令时，仍应使用手动 Raster Pass。

**易错点：**

- 没有在项目代码中看到自定义 `PassData` 不代表没有 PassData；Core SRP 内部使用 `BlitMaterialPassData` 保存源、目标、Material 和 Shader Pass。
- `BlitMaterialParameters` 是提交给封装 API 的配置数据，不是手动 Raster Pass 中由执行回调直接接收的自定义 `PassData`。
- Shader Pass 索引决定运行 Material 中的哪个 Pass；源目标顺序错误会破坏纵向、横向两步处理的依赖。

**现阶段掌握边界：**

- 当前需要掌握：`AddBlitPass()` 是常规全屏纹理处理的封装路径；它与手动 Raster Pass 处于同一 Render Graph 录制层，但代码责任边界不同。
- 暂时不用深挖：`AddUnsafePass` 的内部实现、XR slice / mip 处理和底层图形 API 命令生成。

**验证依据：**

### 概念：`frameData`、`PassData` 与渲染函数的数据边界

**一句话记忆：**

`frameData` 是 URP 提供的当前相机当前帧共享上下文，`PassData` 是自定义节点传给执行回调的数据包，而“渲染函数”就是通过 `SetRenderFunc()` 注册、稍后由 Render Graph 调用的执行回调。

**所在层级：**

URP 的 `ScriptableRenderPass.RecordRenderGraph()` 录制入口与 Core SRP Render Graph 的单节点执行层之间。

**核心职责：**

- `frameData.Get<T>()` 取得 URP 已放入 `ContextContainer` 的本帧相机数据和资源数据。
- `RecordRenderGraph()` 创建节点、填充 `PassData`、声明资源依赖并注册执行回调。
- Render Graph 执行该节点时，把对应 `PassData` 作为参数传给 `SetRenderFunc()` 注册的回调。

**参与流程：**

```text
URP 调用 RecordRenderGraph(renderGraph, frameData)
↓
从 frameData 取得 UniversalResourceData / UniversalCameraData
↓
AddRasterRenderPass<PassData>(..., out passData) 创建节点与数据对象
↓
把 activeColorTexture 等资源句柄写入 passData；这里只复制句柄值，不复制纹理像素
↓
用 builder 声明资源读写和注册 SetRenderFunc
↓
Render Graph 稍后执行该节点
↓
renderFunc(data, context) 接收同一节点的数据并向 context.cmd 记录命令
↓
Unity 提交命令，GPU 运行 Shader
```

**常用入口 / 搭配：**

- `ContextContainer.Get<UniversalResourceData>()`、`Get<UniversalCameraData>()`
- `RenderGraph.AddRasterRenderPass<PassData>()`
- `IRasterRenderGraphBuilder.SetRenderFunc()`、`RasterGraphContext.cmd`

**它不负责什么：**

`frameData` 不是用户自己新建的 Pass 数据，也不代表所有内容都已经完成渲染；`PassData` 不负责跨帧保存资源或自动声明依赖；执行回调是 CPU 记录命令的函数，不是 GPU 上逐像素运行的 Shader。

**易错点：**

- `UniversalResourceData resourceData = frameData.Get<UniversalResourceData>()` 是取得已有上下文，不会创建相机颜色纹理，也不会立即渲染。
- `passData.copySourceTexture = resourceData.activeColorTexture` 只是把同一个 `TextureHandle` 句柄值放进节点参数包；两个字段指向同一个 Render Graph 纹理资源，不会再次获取相机颜色，也不会复制像素。
- `activeColorTexture` 负责表示当前相机颜色资源，`copySourceTexture` 负责把该资源句柄从录制阶段传给稍后的执行回调；二者职责不同，所以逻辑不冲突。

**现阶段掌握边界：**

- 当前需要掌握：能沿着“字段在哪里、谁填充、谁接收、何时执行”追踪 `frameData → RecordRenderGraph → PassData → SetRenderFunc → ExecutePass`。
- 暂时不用深挖：`ContextContainer` 内部存储、PassData 对象池、Render Graph 编译器与线程调度细节。
